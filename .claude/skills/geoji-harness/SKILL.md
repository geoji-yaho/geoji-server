# geoji-harness

10(`docs/10-backend-contract.md`)의 절 하나 또는 §0.1 할 일 묶음을 코드로 만드는 순서다. 명세를 대조하고 구현한 뒤 테스트로 검증한다.

혼자 다 하지 않는 이유는 둘이다. 명세 대조와 구현을 한 눈이 하면 10 에 없는 값을 자기도 모르게 채운다. 구현한 눈이 검증하면 자기가 만든 것을 옳다고 읽는다.

코드 리뷰는 하네스에 넣지 않는다. 매 작업마다 리뷰 에이전트를 부르면 토큰이 크게 들어서 뺐다. 리뷰는 사용자가 필요할 때 직접 `/code-review`로 돌린다. 오케스트레이터가 알아서 돌리지 않는다.

geoji-agent 하네스와 다른 점. 10 은 계약만 정하고 Java 파일 경로를 정하지 않는다. 그래서 명세 대조가 현재 서버 코드와 10 을 맞대어 파일 목록을 **제안**하고, 새 패키지·테이블·의존성은 게이트 B 에서 승인받는다. 테스트 목록은 계획서 §4.2 대신 10 §13 수용 검사와 각 절의 결과·거부 표다. 그리고 10 은 읽기 전용 사본이라, 구현하며 생긴 회신은 10 을 고치지 않고 보고서에 모은다.

## 쓰는 도구

`Agent`와 `SendMessage`다. 에이전트 정의는 `.claude/agents/`에 있고 `subagent_type`에 파일 이름을 확장자 없이 넣는다.

| subagent_type          | 하는 일                                          | 산출                                     |
| ---------------------- | ------------------------------------------------ | ---------------------------------------- |
| `geoji-spec-auditor`   | 10 과 서버 코드에서 무엇을 어디에 만들지 확인, 미결 판정 | `_workspace/01_spec.md`                  |
| `geoji-implementer`    | Java 코드와 테스트 작성                          | 소스·테스트 파일, `_workspace/02_impl.md` |
| `geoji-test-verifier`  | 케이스와 테스트 대조, Gradle 게이트, 격리 확인   | `_workspace/03_test.md`                  |

호출은 이렇게 한다. `model`은 셋 모두 `opus`다.

```
Agent({
  subagent_type: "geoji-spec-auditor",
  name: "spec",
  model: "opus",
  description: "명세 대조",
  prompt: "..."
})
```

`_workspace/`는 `.gitignore`에 있어 커밋되지 않는다. 중간 산출물을 남겨 두면 후속 요청에서 처음부터 다시 하지 않아도 된다.

일이 끝난 에이전트는 `SendMessage`로 `shutdown_request`를 보내 정리한다. 에이전트 정의의 `tools`에 `SendMessage`가 없으면 그 에이전트는 응답하지 못해 세션이 남는다. 도구를 좁힐 때 이것을 빼지 않는다.

## 두 가지 실행 모드

| 모드      | 어떻게 아는가                                              | 질문 상대            | 끝                       |
| --------- | ---------------------------------------------------------- | -------------------- | ------------------------ |
| 사람 세션 | 보통                                                       | `AskUserQuestion`    | 보고하고 한 줄 묻는다    |
| orca 워커 | 프롬프트 첫머리에 Task ID·Dispatch ID 가 든 orca preamble  | preamble 의 `ask`    | 커밋·PR·`worker_done`    |

아래 Phase 는 두 모드가 같다. 다른 곳은 게이트 A·B 의 질문 상대와 Phase 4 뒤의 마무리이고, 그것은 맨 아래 "orca 워커 모드" 절에 있다.

## 게이트

```bash
./gradlew build
```

통과해야 완료다. 두 가지 알려진 상태가 있다.

- JDK 25 가 없으면 Gradle 이 뜨지 않는다. 게이트를 못 돌린 것으로 보고하고 통과로 적지 않는다
- 기존 `contextLoads` 는 DB 없이 실패한다(테스트 DB 미정, `testing` 룰). 이것만 실패하면 "기존 실패 1건"으로 구분해 적고, 새 테스트는 `./gradlew test --tests '<클래스>'` 로 따로 통과를 확인한다

## Phase 0. 어디서 시작할지 정한다

`_workspace/`를 보고 실행 모드를 고른다.

| 상태                           | 모드        | 시작 지점                                           |
| ------------------------------ | ----------- | --------------------------------------------------- |
| `_workspace/` 없음             | 초기        | Phase 1                                             |
| 있고 같은 대상을 고치라는 요청 | 부분 재실행 | 고칠 단계부터. 뒤 단계는 다시 돈다                  |
| 있고 다른 대상 요청            | 새 실행     | `_workspace/`를 `_workspace_prev/`로 옮기고 Phase 1 |

그리고 규모를 판정한다. 작은 일에 셋을 부르면 기다리는 시간이 만드는 시간보다 길어진다.

| 규모 | 무엇                                   | 부르는 에이전트                                         |
| ---- | -------------------------------------- | ------------------------------------------------------- |
| 작음 | §0.1 한 줄. 파일 한두 개(예: payload 키 하나, 오류 코드 하나) | implementer, test-verifier. 명세 대조는 직접 한다 |
| 보통 | 10 의 절 하나(예: §4.3 begin-generation, §6 watchdog) | 셋 전부. 구현은 1명                    |
| 큼   | 여러 절에 걸친 흐름(예: §3+§5+§6 판결 확정 전체) | 셋 전부. 구현은 파일을 나눠 최대 3명    |

규모를 정했으면 사용자에게 한 줄로 알린다. 무엇을 만들고 누구를 부르는지.

## Phase 1. 명세를 대조한다

`geoji-spec-auditor` 1명. 요청 원문과 짐작되는 절을 넘긴다.

```
prompt: |
  요청: {사용자 원문}
  짐작되는 10 절·§0.1 줄: {10 §4.3, §0.1 9/14 D-24 줄 또는 "모르겠음"}

  docs/10-backend-contract.md 의 해당 절과 §0.1·§13·§14·§15, 현재 서버 코드에서
  대상을 확정하고 _workspace/01_spec.md에 정의된 형식으로 쓴다.
  (제안)·§14 미결·스키마 위치·서버 이름 어긋남에 걸리면 blocked 절에 남기고 임시 기본값을 제안하지 않는다.
```

## 게이트 A. 미결이면 멈추고 묻는다

`_workspace/01_spec.md`의 `blocked`가 비어 있지 않으면 **여기서 멈춘다.** `AskUserQuestion`으로 묻고 답을 받은 뒤에 진행한다. orca 워커 모드면 스펙의 "미리 답한 결정"으로 먼저 풀고, 남는 것만 preamble 의 `ask`로 코디네이터에게 묻는다.

이 저장소는 10 에 없는 값을 코드에 박기 전에 묻기로 되어 있다. 협의 중인 값에 그럴듯한 기본값을 채우면 그것이 사실상 확정이 되고, AI 파트 워커는 다른 동작을 기대한 채 돈다.

자주 걸리는 것.

- 10 의 `(제안)`(D-24 SENTENCE 게이트, D-26 진행 중 job 끄기, §4.4 매핑 통지, §5 10단계 강도 집합). 백엔드가 채택을 정해야 한다
- 10 §14 미결 행(watchdog 뒤 이전 job 상태, 422 전용 코드, `burn_rate` 단위 등)
- 004 DDL 의 위치와 적용 주체, 테스트 DB 방식(`code-layout`·`testing` 룰)
- 10 의 `posts`·`verdicts` 와 서버 `expenses`·`expense_trials` 의 대응(`domain-vocabulary` 룰 어긋남 표)
- AI 쪽에 아직 없는 것(10 §16.3 이미지·compose, §4.4 `/linked`)

질문에는 선택지를 함께 낸다. 무엇이 왜 막혔고 각 선택이 무엇을 바꾸는지, AI 파트에 회신이 필요한지 적는다.

## 게이트 B. 승인이 필요하면 묻는다

`_workspace/01_spec.md`의 `approval`이 비어 있지 않으면 멈추고 묻는다. `build.gradle` 의존성 추가, 새 패키지·계층, 새 테이블·컬럼(DDL), `SecurityConfig`·`ApiExceptionHandler` 변경, 기존 공개 API 응답 모양 변경, 기존 `AiClient`·재판 흐름 제거가 여기 해당한다.

`approval`이 비어 있으면 사용자를 부르지 않고 Phase 2로 간다. orca 워커 모드의 질문 상대는 게이트 A 와 같다.

## Phase 2. 구현한다

`geoji-implementer`. 테스트도 구현 몫이다. 규모가 큼이면 파일 목록을 겹치지 않게 나눠 최대 3명까지 한 메시지에서 동시에 부른다. 같은 파일을 둘에게 주지 않는다. `orca-worker` 룰의 공유 자원(`SecurityConfig`, `application.yml`, `build.gradle`, `API.md`)은 한 명에게만 준다.

```
prompt: |
  _workspace/01_spec.md를 읽고 구현한다.
  네 몫: {파일 목록. 소스와 테스트}
  다른 담당이 맡은 파일: {목록}. 건드리지 않는다.
  게이트 A·B에서 정해진 것: {사용자 답변, 없으면 "없음"}
  _workspace/02_impl.md에 보고를 쓴다. 여럿이면 02_impl_{n}.md에 쓴다.
```

## Phase 3. 테스트로 검증한다

`geoji-test-verifier` 하나를 부른다. 케이스와 테스트를 대조하고 게이트를 돌린다. 코드 검토 에이전트는 없다. 잠금 순서·enum·내부 API 규약은 구현자가 `.claude/rules/`로 지키고, 리뷰는 사용자가 나중에 돌린다.

```
prompt: |
  방금 구현한 것을 검토한다. _workspace/의 02_impl*.md 전부에 목록이 있다.
  이번에 쓴 보고서: {실제 파일 목록}
  자기 담당 파일에 정해진 형식으로 쓴다.
```

## Phase 4. 고치고 보고한다

테스트 검증 보고서를 읽고 오케스트레이터가 직접 고친다. 고치는 에이전트를 또 부르지 않는다.

1. 같은 줄이나 같은 원인을 가리키는 지적을 하나로 합친다
2. 심각도 높음부터 고친다
3. 고치지 않는 것은 이유를 적는다. 10 과 다른 동작이 되거나 이번 범위 밖이면 넘긴다
4. 게이트를 다시 돌린다. 통과할 때까지 고친다
5. 같은 게이트가 세 번 반복 실패하면 더 시도하지 않는다. 변경을 되돌리고 명세로 돌아간다

보고는 이렇게 한다.

```markdown
## 만든 것

| 경로 | 무엇 | 10 절 |

## 검증

| 관점   | 판정 | 남은 것 |
| 테스트 |      |         |

## 고친 것

## 넘긴 것

반영하지 않은 것과 이유.

## 확인하지 못한 것

DB 없이 못 본 SQL·잠금·경합, mock 으로만 본 AI API, JDK 가 없어 못 돌린 게이트, 미결이라 비워 둔 값.

## AI 파트 회신

`backend-contract` 룰 형식. 구현한 §0.1 줄(반영 제안), §14 에 생긴 답, 10 과 다르게 된 것. 없으면 "없음". AI 저장소 10 으로 옮기는 것은 사용자가 한다.
```

공개 API 를 바꿨으면 `API.md` 가 같이 고쳐졌는지 확인한다. 커밋하지 않는다. 10 사본은 고치지 않는다.

마지막에 한 줄로 묻는다. 고칠 곳이 있는지, 워크플로우에서 바꾸고 싶은 것이 있는지.

orca 워커 모드는 위 두 문단 대신 아래 "orca 워커 모드" 절의 마무리를 따른다.

## orca 워커 모드

orca 코디네이터가 `worker-start`로 워크트리에 띄운 세션이다. 프롬프트 첫머리에 Task ID·Dispatch ID 와 `ask`·`send`·`check` 명령이 든 preamble 이 있다. 그 preamble 이 있을 때만 이 절이 적용되고, 위 Phase 에 우선한다. 불변 규칙은 `orca-worker` 룰에 있다.

원칙은 하나다. **사람은 이 터미널을 보고 있지 않다.** 로컬에서 묻는 것은 전부 코디네이터에게 `ask`로 보낸다. 훅이 `AskUserQuestion`을 막는다. preamble 의 명령은 그대로 복사한다. 플래그를 재구성하지 않는다.

**시작할 때.**

1. preamble 에 든 작업 스펙을 `_workspace/orca/spec.md`에 그대로 저장한다. 훅이 이 파일의 Ownership JSON 블록으로 편집 범위를 지키고, 이 파일이 있어야 워커 모드로 본다
2. `java -version` 으로 JDK 25 가 있는지 본다. 없으면 게이트를 못 돌린다는 것을 첫 `check` 전에 알고 시작한다
3. 스펙의 "미리 답한 결정"을 게이트 A·B 의 답으로 쓴다. Phase 0 은 스펙의 파일 수로 규모를 정한다

**체크포인트.** Phase 가 바뀔 때마다와 게이트를 돌린 뒤 preamble 의 `check --terminal <handle>` 을 돌린다. 코디네이터의 후속 지시가 있으면 따른다. `consumer_fenced`가 오면 즉시 멈추고 아무것도 보내지 않는다. 이 Dispatch 는 더 이상 내 것이 아니다.

**질문.** 게이트 A·B 에서 스펙이 답하지 못한 것은 `ask --question ... --options a,b`로 묻고 답이 올 때까지 기다린다. 타임아웃이면 같은 message ID 로 `--resume`. 새 질문을 만들지 않고 임시값도 넣지 않는다.

**게이트.** DB 가 필요한 테스트는 스펙이 테스트 DB 를 주지 않았으면 쓰지 않는다. 이유는 `orca-worker` 룰.

**Phase 4 뒤 마무리.**

1. 위 보고 형식을 `_workspace/04_report.md`에 쓴다. "확인하지 못한 것"에 DB·JDK 사정을, "AI 파트 회신"에 10 과 다른 것을 적는다
2. `git-workflow` 룰 "orca 워커" 절대로 커밋 → 리베이스 → 푸시 → PR
3. `check`를 한 번 더 돌려 후속 지시가 없는지 본다
4. `worker_done`을 정확히 한 번. `--outcome succeeded|failed`, `--report-path <04_report.md 절대 경로>`, `--files-modified`. body 는 세 문장. 만든 것, 발견한 것, 남은 것과 PR URL
5. `_workspace/orca/done` 파일을 만든다. Stop 훅이 이 파일 없이는 턴을 끝내지 못하게 한다
6. 턴을 끝내고 대기한다. 새 일을 시작하지 않는다

**실패로 끝날 때도 1~6 은 같다.** 게이트 3회 실패, 스펙 밖 파일이 꼭 필요한데 `ask`로 못 받음, 미결에 막힘이 그 경우다. 커밋·PR 은 되는 데까지 하고 `--outcome failed`와 이유를 body 에 쓴다. 조용히 종료하지 않는다.

하위 에이전트(spec-auditor 등)는 그대로 쓴다. orca 가 보는 것은 이 터미널 하나뿐이고 하위 에이전트는 preamble 을 모르므로, `ask`·`check`·`worker_done`은 오케스트레이터인 내가 보낸다.

## 에러

| 무슨 일                          | 어떻게                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| 에이전트가 빈 결과나 실패를 반환 | 같은 프롬프트로 한 번만 다시 부른다. 또 실패하면 그 단계 없이 진행하고 보고서에 누락을 적는다 |
| 산출 파일이 없음                 | 다음 단계를 시작하지 않는다. 앞 단계를 다시 부른다                                            |
| 검증 지적이 10 과 어긋남         | 지우지 않는다. 양쪽을 보고서에 함께 적고 어느 쪽을 따랐는지 밝힌다                            |
| 게이트 3회 반복 실패             | 되돌리고 명세로 돌아간다. 네 번째를 시도하지 않는다                                           |
| 10 사본이 정본과 다름            | 구현을 시작하지 않는다. 사용자에게 동기화를 먼저 묻는다                                      |
| 테스트가 공유 DB·실제 AI API 를 부르려 함 | 접속 정보를 넣어 통과시키지 않는다. mock 으로 바꾸거나 DB 필요 케이스로 보류한다      |

## 테스트 시나리오

**정상.** "10 §4.3 begin-generation 만들어줘"가 들어온다. Phase 0이 보통 규모로 판정한다. spec-auditor 가 요청·응답·거부 표를 옮기고, 서버에 `verdicts` 가 없고 `expense_trials` 에 `verdict_version`·`active_generation_id` 가 없다는 것을 `기존 코드 대응`과 `blocked`에 적는다. 오케스트레이터가 멈추고 묻는다. `expense_trials` 에 컬럼을 더할지, 10 대로 `verdicts` 를 새로 만들지, DDL 은 어디에 둘지. 답을 받은 뒤 implementer 가 내부 API 컨트롤러와 `@WebMvcTest` 거부 케이스(409 `STALE_GENERATION`·`DEADLINE_EXCEEDED`, 404)를 쓴다. test-verifier 가 `DEADLINE_EXCEEDED` 케이스가 상태 코드만 보고 `code` 를 안 본다고 잡는다. 고치고 게이트를 돌린 뒤 보고하고, "AI 파트 회신"에 §14 "내부 API 상태 기계" 행의 답을 적는다.

**게이트 A.** "D-24 SENTENCE 게이트 붙여줘"가 들어온다. spec-auditor 가 10 §3 의 게이트가 `(제안)` 이고 §14 에 9/16 기한으로 올라 있으며, 보류 중 삭제 행도 미결임을 `blocked`에 넣는다. 오케스트레이터가 채택 여부와 보류 중 삭제 처리를 묻는다. 답을 받기 전에 대기 30초나 스캔 주기를 임의로 정하지 않는다.
